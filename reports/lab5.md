# 实验五：线程、同步与死锁检测

## 功能总结

实现进程级死锁检测开关，分别为互斥锁和信号量维护可用资源、线程持有量和待满足请求。申请前运行资源消除算法，无法找到安全完成序列时撤销请求并返回 -0xDEAD。关闭检测时仍记录资源变化，支持随后开启。时间写回逐页检查用户权限；非法资源编号和非法开关参数返回 -1。

## 资源消除算法

复制 Available 为 Work，将所有线程标记为未完成。反复寻找 Need 不大于 Work 的线程，将它的 Allocation 加回 Work 并标记完成。若所有线程都可完成，则保留新请求；否则只撤销本次 Need 增量，不修改实际锁或信号量。申请成功返回后才更新 Allocation，阻塞期间保留 Need，唤醒后继续提交。互斥锁和信号量分别计算，不检测跨类别、条件变量或 waittid 形成的复合等待环。

信号量允许未持有资源的线程执行 up，不能对其持有计数无条件减一。条件变量等待会释放再获取互斥锁，统计也同步释放再获取。线程 ID 回收时清空旧行，避免 ID 重用继承旧统计；线程退出不自动解锁，未归还资源仍保持不可用。

## 主线程退出的资源回收

需要回收进程地址空间中的代码、数据、堆、线程用户栈和 trap context 页面，页表及其物理帧，所有线程内核栈与 TCB，线程 ID、文件描述符、同步对象及其等待队列、进程父子关系与 PID 管理项。当前执行线程的内核栈不能立即释放，必须切换到其他栈后再回收。

TCB 可能被进程的 tasks 表、全局就绪队列、处理器 current、定时器队列、互斥锁/信号量/条件变量等待队列引用。必须从全局调度和定时器容器移除退出进程的线程，避免再次调度或唤醒；进程内部的等待队列可随同步对象统一释放，但应注意同步对象到 TCB、TCB 到进程采用弱引用，避免循环引用。已经退出但尚未 waittid 的线程可保留退出状态供回收，不能仍持有可运行所需的用户资源。

## 两种互斥锁实现

Mutex1 解锁时将 locked 设为 false，再唤醒队首线程。被唤醒线程必须重新检查并竞争锁；其他线程可能先获得锁，因此 while 重试是必要的。其正确性依赖检查和入队的原子性，且可能存在插队及饥饿。

Mutex2 有等待者时保持 locked=true，将所有权直接交给被唤醒线程。唤醒后不再重复获取，防止插队，等待队列可提供近似 FIFO 公平性。该实现要求唤醒准确对应一次所有权转移；若错误地套用 Mutex1 的重试循环，线程会把已交给自己的锁当作被占用并再次阻塞。反过来，Mutex1 如果省略循环，可能在其他线程已持锁时也进入临界区。
